# สเปก UI: วิเคราะห์ผลผู้เรียนและ Pre-test / Post-test

สถานะ: ข้อกำหนด UX/UI สำหรับให้ AI หรือทีมพัฒนานำไปทำต่อ ยังไม่ใช่การอนุมัติกฎธุรกิจ Production
ขอบเขต: ต้นแบบ React/Vite ที่ `D:\code\elearn-prod\elearning-ux-v2`; เอกสารฉบับนี้อยู่ใน checkout แยกเพื่อไม่แตะงานค้างของ checkout หลัก
ตรวจ source เป้าหมาย ณ 30 กันยายน 2026; ไม่เพิ่ม backend, event tracking หรือระบบวิเคราะห์จริงในเอกสารนี้

## 1. สรุปสิ่งที่มีและช่องว่าง

### มีอยู่แล้วใน checkout เป้าหมาย

- มีหน้ารายการแบบทดสอบและผลรายแบบทดสอบที่ผู้สอนเปิดดู attempt ได้ (`/teach/quizzes/:quizId/attempts`)
- มีหน้าตรวจข้อเขียนราย attempt (`/teach/attempts/:attemptId/grade`) และหน้าผลให้ผู้เรียนดูคำตอบของตน
- attempt ปัจจุบันเชื่อม `quizId`, `courseId`, `userId` และข้อมูลคะแนน/สถานะข้อเขียนได้ จึงเริ่มจากผลแบบฝึกหัดรายคอร์สได้
- ข้อมูลและบัญชีเป็นต้นแบบที่บันทึกใน browser; ยังไม่มี event tracking เวลาเรียน/ดูวิดีโอ

### ยังไม่มีใน checkout เป้าหมาย

- ไม่มีหน้า `/teach/analytics` หรือ `/admin/analytics` และไม่มี read-model `src/api/analytics.js`
- ไม่มี assignment manager/inbox สำหรับมอบหมายแบบฝึกหัดให้ผู้เรียนรายคนหรือกลุ่ม
- ยังมีเพียงทางเข้าตรวจจากแบบทดสอบทีละรายการ ไม่มีกล่องคิวตรวจส่วนกลาง
- ไม่มีตาราง/หน้ารายผู้เรียนที่เชื่อม enrollment, ความคืบหน้า, งานที่ส่ง, คะแนน และ feedback
- ไม่มีชนิด Pre-test / แบบวัดระหว่างเรียน / Post-test, comparison set หรือการจับคู่ผลของผู้เรียนคนเดียวกัน
- ไม่มี event ข้อมูลเวลาเรียน วิดีโอที่ดู หรือการไม่ส่งก่อนกำหนด; due date/overdue ก็ยังไม่ได้กำหนด

ข้อสรุป: ใช่—Analytics รายผู้เรียนและ Pre/Post ยังไม่มีใน checkout หลัก ส่วนการเปิดดูคำตอบและตรวจข้อเขียนมีแล้วแต่แยกตามแบบทดสอบ/attempt เท่านั้น การเปลี่ยนแปลงใน checkout แยกจากงานรอบก่อนยังไม่อยู่ใน checkout เป้าหมาย จึงห้ามสมมติว่ามี route หรือไฟล์เหล่านั้นแล้ว

ห้ามทำให้ fixture ดูเหมือนข้อมูล Production และห้ามอนุมานเวลาเรียน/การมีส่วนร่วมจากการเปิดหน้าเว็บหรือสถานะจบเนื้อหา

## 2. เป้าหมายและผู้ใช้

**เป้าหมาย:** ช่วยผู้สอนรู้ว่าใครต้องการความช่วยเหลือ งานใดต้องตรวจ และผู้เรียนเปลี่ยนแปลงผลการประเมินอย่างไร; ช่วยแอดมินเห็นภาพรวมคอร์สโดยไม่ขยายสิทธิ์ผู้สอนข้ามคอร์ส

- ผู้สอน: เห็นเฉพาะคอร์สที่ตนรับผิดชอบ; เข้าคิวตรวจและดูรายละเอียดผู้เรียนในคอร์สของตน
- แอดมิน: เห็นภาพรวมทุกคอร์ส กรองตามคอร์ส/ผู้สอน และเจาะข้อมูลเฉพาะเมื่อจำเป็น
- ผู้เรียน: ไม่เพิ่มหน้า Analytics สำหรับผู้อื่น; ผู้เรียนยังดูผลและ feedback ของตนผ่านหน้าผลแบบฝึกหัดเดิม

## 3. Information architecture และ route ที่เสนอ

เพิ่ม Analytics เป็นทางเข้าภาพรวม แล้วเพิ่มระดับ drill-down ดังนี้ (รายการที่ระบุว่า “มีแล้ว” คือ route ปัจจุบันใน checkout เป้าหมาย):

| บทบาท | หน้า | จุดประสงค์ |
| --- | --- | --- |
| ผู้สอน | `/teach/analytics` (ใหม่) | ภาพรวมคอร์สของฉัน, งานรอตรวจ และทางเข้า analytics รายคอร์ส |
| ผู้สอน | `/teach/courses/:courseId/analytics` (ใหม่) | วิเคราะห์ผลและความคืบหน้าของคอร์สเดียว; มีแท็บภาพรวม, แบบฝึกหัด, ผู้เรียน, Pre/Post |
| ผู้สอน | `/teach/courses/:courseId/analytics/learners/:learnerId` (ใหม่) | Timeline และผลของผู้เรียนคนนี้ในคอร์สนี้เท่านั้น |
| ผู้สอน | `/teach/reviews` (ใหม่) | คิวงานข้อเขียน/ภาพที่รอตรวจ รวมข้ามแบบฝึกหัดในคอร์สที่ดูแล |
| ผู้สอน | `/teach/assignments` (ใหม่) | มอบหมายแบบฝึกหัดจากคอร์สให้ผู้เรียนที่ลงทะเบียน; กำหนดผู้รับอย่างชัดเจน |
| ผู้สอน | `/teach/quizzes/:quizId/attempts` และ `/teach/attempts/:attemptId/grade` (มีแล้ว) | คงเป็นหน้ารายการคำตอบและหน้าตรวจราย attempt; เชื่อมกลับคิวตรวจ/analytics |
| ผู้เรียน | `/learn/assignments` (ใหม่) | กล่องงานที่ผู้สอนมอบหมายให้ผู้เรียนคนนั้น; ดูสถานะ/เริ่ม/ทำต่อ/ดูผล |
| แอดมิน | `/admin/assignments` (ใหม่) | จัดการงานมอบหมายข้ามคอร์สตามสิทธิ์แอดมิน |
| แอดมิน | `/admin/analytics` (ใหม่) | ภาพรวมระบบและตัวกรองคอร์ส/ผู้สอน |
| แอดมิน | `/admin/analytics/courses/:courseId` (ใหม่) | ดู analytics รายคอร์ส รวมถึงคอร์สที่แอดมินไม่ได้เป็นผู้สอน |
| แอดมิน | `/admin/analytics/courses/:courseId/learners/:learnerId` (ใหม่) | เจาะผู้เรียนตามคอร์สที่เลือก; แสดงชื่อคอร์สและผู้สอนตลอดเวลา |

รายการ route เป็นข้อเสนอสำหรับต้นแบบ; ก่อน implement ให้ตรวจ route ปัจจุบันและใช้ component เดิมเมื่อทำได้ ห้ามทำหน้า duplicate ที่คำนวณ metric คนละสูตร

### ลำดับทำงานที่แนะนำ

1. เพิ่ม assignment และการผูก quiz ↔ course ↔ ผู้เรียน เพื่อรู้ denominator/ผู้มีสิทธิ์ส่งงาน
2. รวมคิวตรวจข้อเขียน/ภาพ โดย reuse หน้าตรวจเดิม
3. เพิ่ม analytics ระดับคอร์สและรายผู้เรียน พร้อม metric dictionary เดียว
4. เพิ่ม metadata ชุด Pre/Post และรายงานแบบ paired; จากนั้นเปิดภาพรวมข้ามคอร์สให้แอดมิน

อย่าข้ามข้อ 1 แล้วคำนวณ submission rate จาก attempt อย่างเดียว เพราะจะไม่รู้ว่าใครถูกคาดหวังให้ส่ง

## 4. หน้าภาพรวมผู้สอนและแอดมิน

### ผู้สอน `/teach/analytics`

ลำดับบนลงล่าง:

1. ชื่อ “วิเคราะห์การเรียนรู้” พร้อมตัวเลือกคอร์ส; ค่าเริ่มต้นเป็น “ทุกคอร์สของฉัน”
2. แถวสรุปแบบกะทัดรัด: ผู้เรียนที่ลงทะเบียน, ผู้เรียนที่เรียนจบ, งานที่ส่งในช่วงที่เลือก, งานรอตรวจ
3. ส่วน “ต้องติดตาม”: งานรอตรวจที่เก่าที่สุด, งานที่ยังไม่ส่ง (เฉพาะเมื่อกำหนดวันครบกำหนดแล้ว), ผู้เรียนที่ยังไม่เริ่ม/ความคืบหน้าต่ำ โดยแสดงเกณฑ์ที่ใช้
4. ตารางรายคอร์ส: คอร์ส, จำนวนผู้เรียน, completion, submissions, pending review, pass rate, ปุ่ม “ดูผลคอร์ส”
5. แนวโน้มกิจกรรมที่มีข้อมูลจริงใน fixture พร้อมช่วงเวลา/ฐานการนับชัดเจน

การกดจำนวนรอตรวจต้องเปิด `/teach/reviews` พร้อม filter คอร์ส/สถานะที่ตรงกัน; การกดแถวคอร์สเปิด Analytics ของคอร์สนั้น

### แอดมิน `/admin/analytics`

- เริ่มที่ภาพรวมระบบแบบ aggregate; มีตัวกรองผู้สอน, คอร์ส, ช่วงเวลา และสถานะคอร์ส
- ตารางรายคอร์สใช้ metric definition เดียวกับผู้สอน พร้อมชื่อผู้สอน
- drill-down ไปคอร์สและผู้เรียนได้ แต่ทุกหน้าต้องแสดง context ว่ากำลังดูคอร์ส/ผู้สอนใด
- ไม่เปิดรายชื่อผู้เรียน/PII ทั้งระบบเป็นค่าเริ่มต้น; ใช้ aggregate ก่อน แล้วค่อยเข้า learner detail ในขอบเขตคอร์ส
- ไม่มีปุ่ม export ข้อมูลผู้เรียนใน MVP นี้

## 5. หน้า Analytics รายคอร์ส

Header แสดง breadcrumb `Analytics > ชื่อคอร์ส`, ชื่อผู้สอน (จำเป็นในหน้าแอดมิน), จำนวนผู้เรียน และตัวกรองช่วงวันที่/บท/แบบฝึกหัด ใช้ Tabs หรือ Segmented ที่มี label ชัด ไม่ทำทุกหมวดเป็น card grid

### แท็บ “ภาพรวม”

- enrollment count และจำนวนผู้เรียนที่มี activity ที่บันทึกได้
- completion rate พร้อมนิยาม “เรียนจบ” และฐานจำนวนผู้เรียน
- assignment/quiz submission rate และ pending grading แยกจากกัน
- คะแนนภาพรวมแสดง average และ median เป็น %; แสดงจำนวน attempt/ผู้เรียนที่นำมาคำนวณ
- สถานะผู้เรียน: ยังไม่เริ่ม / กำลังเรียน / รอตรวจ / ผ่าน / ยังไม่ผ่าน
- ปุ่ม/ลิงก์จากแต่ละ metric ไปยังตารางที่กรองตรงกัน

### แท็บ “คะแนนและแบบฝึกหัด”

- ตารางต่อแบบฝึกหัด: ชื่อ, stage (ถ้ามี), ส่งแล้ว/ผู้รับที่มีสิทธิ์, รอตรวจ, average, median, pass rate, จำนวนที่มีคะแนนสมบูรณ์
- คลิกแบบฝึกหัดเพื่อเปิดผลราย attempt และคำถาม; ข้อเลือกตอบแสดงสัดส่วนตอบถูกต่อข้อเมื่อมีข้อมูลพอ
- ข้อเขียนและภาพแสดง pending แยกจาก graded; ห้ามนับ pending เป็นศูนย์คะแนนหรือเป็นผู้ไม่ผ่าน
- หากอนุญาตให้ลองหลายครั้ง แสดงจำนวนครั้งและสูตรเลือกคะแนนอย่างเปิดเผย ห้ามรวมทุก attempt เป็นเสมือนคนละผู้เรียน

### แท็บ “ผู้เรียน”

ตารางค้นหา/กรองด้วยชื่อหรืออีเมล, สถานะเรียน, สถานะส่งงาน, ช่วงความคืบหน้า และผลการประเมิน

คอลัมน์ขั้นต่ำ: ชื่อผู้เรียน, ความคืบหน้าคอร์ส, งานที่ส่ง/ที่มอบหมาย, งานรอตรวจ, คะแนนล่าสุดของ assessment ที่เลือก, activity ล่าสุดที่มี timestamp จริง และ action “ดูรายละเอียด”

แสดงตารางแบบ responsive (บนจอแคบใช้ overflow ที่ตั้งใจหรือ row summary แบบยุบได้) ไม่ซ่อน action ไว้เฉพาะ hover

## 6. หน้า Analytics รายผู้เรียน

- Header: ชื่อผู้เรียน, คอร์ส, ผู้สอน, สถานะ enrollment; breadcrumb กลับหน้ารายคอร์ส
- Summary: ความคืบหน้าคอร์ส, งานส่งแล้ว/ทั้งหมดที่มอบหมาย, งานรอตรวจ, คะแนนประเมินล่าสุด
- Timeline ตามเวลา: เริ่ม/ส่ง attempt, ผู้สอนตรวจ, คะแนนและ feedback; แสดงเฉพาะ event ที่มีใน data
- ตารางผล assessment: ชื่อ, stage, คะแนนดิบ, คะแนน %, วันที่ส่ง, สถานะ grading, จำนวน attempt
- Link ไปดูคำตอบและ rubric ได้ตาม permission; ผู้สอนเห็นเฉพาะ course ของตน, admin เห็นตามสิทธิ์ admin
- ห้ามแสดงคำตอบของผู้เรียนคนอื่นหรือ answer key ที่ไม่จำเป็นต่อหน้าที่นี้
- สถานะ “ไม่มีข้อมูล”, “กำลังรอตรวจ”, “ไม่มี enrollment”, “ไม่พบผู้เรียนในคอร์สนี้” ต้องต่างกันชัดเจน

## 7. คิวตรวจ `/teach/reviews`

คิวนี้มีไว้ทำงาน ไม่ใช่รายงานสถิติ:

- ค่าเริ่มต้นแสดง `รอตรวจ`; มี filter คอร์ส, แบบฝึกหัด, ประเภทคำตอบ, วันที่ส่ง และผู้เรียน
- คอลัมน์: ผู้เรียน, งาน/แบบฝึกหัด, คอร์ส, เวลาส่ง, อายุรายการรอตรวจ, สรุปชนิดคำตอบ (ข้อความ/ภาพ), ปุ่ม “ตรวจคำตอบ”
- เรียงรายการเก่าก่อน; ถ้ายังไม่มี due date ห้ามติดป้าย overdue
- หลังบันทึกคะแนน กลับคิวเดิมและรักษา filters; สถานะเปลี่ยนเป็น “ตรวจแล้ว” และ Analytics คำนวณใหม่
- หน้าตรวจเดิมต้องยังใช้ได้จากคิวและหน้ารายแบบทดสอบ
- ถ้าไม่มีรายการ: empty state อธิบายว่าไม่มีคำตอบรอตรวจ; ถ้ากรองแล้วไม่พบ ให้เสนอ “ล้างตัวกรอง”

## 8. Pre-test / Post-test: UX และนิยามการคำนวณ

### การตั้งค่า assessment

เพิ่มชนิดการวัดให้แบบฝึกหัด: `Pre-test`, `ระหว่างเรียน`, `Post-test`, `ไม่จัดเป็นการวัดผล` และ field “ชุดเปรียบเทียบ” (เช่น ทักษะการสื่อสาร รุ่น ก.ย. 2026) เพื่อระบุคู่ที่ตั้งใจเทียบ ไม่ใช้ชื่อ quiz มาเดาเอง ต้องเชื่อมกับคอร์สและ assignment/ผู้รับที่ชัดเจน เพื่อคำนวณผู้มีสิทธิ์ทำและผู้ที่ยังไม่มีผลได้

แบบทดสอบในชุดเดียวกันควรเทียบวัตถุประสงค์การเรียนรู้และเกณฑ์คะแนนได้ หากข้อสอบ/คะแนนเต็มต่างกัน ให้ normalize เป็น % และแสดงคำเตือนถ้าไม่มี blueprint/learning objectives ที่ตรงกัน

### หน้ารายงาน Pre/Post

- เลือกชุดเปรียบเทียบและคอร์ส; แสดงชื่อ Pre-test และ Post-test ที่ถูกจับคู่
- แสดงจำนวนผู้เรียนที่มี Pre, มี Post, มีครบทั้งคู่, ยังขาดผล และมีข้อเขียนรอตรวจ
- แสดงคะแนนเฉลี่ยก่อน/หลัง, median ก่อน/หลัง, และค่าเฉลี่ยของ “ส่วนต่างคะแนนรายคน” เป็น percentage points
- แสดง distribution ก่อน/หลังและตารางรายผู้เรียนที่ drill ไปดูรายละเอียดได้
- ค่าไม่มีข้อมูลใช้ “—” พร้อมเหตุผล ไม่แสดง `0%` แทนข้อมูลหาย
- ระบุว่าเป็น “การเปรียบเทียบผู้เรียนที่มีผลครบทั้งคู่” ไม่อ้างว่าคอร์สเป็นสาเหตุให้คะแนนเพิ่ม

### สูตรและข้อควรระวัง

- `คะแนน% = คะแนนที่ได้ / คะแนนเต็มที่ใช้ตัดสิน × 100`
- `ส่วนต่างรายคน (จุดเปอร์เซ็นต์) = Post% - Pre%`
- ค่า “ส่วนต่างเฉลี่ย” คำนวณจากผู้เรียนที่มีผล valid ทั้ง Pre และ Post คนเดียวกันเท่านั้น; แสดง matched n เสมอ
- รายการที่ยังรอตรวจข้อเขียนไม่ใช่ valid final score; แยกเป็น pending และยังไม่นำเข้าคะแนนเปรียบเทียบ
- ผลจาก cohort ที่ทำไม่ครบทั้งคู่ไม่ควรรวมเป็น paired gain; แสดง coverage เพื่อไม่ให้กลุ่มตัวอย่างที่เหลือถูกเข้าใจว่าแทนทุกคน
- ไม่เรียกผลต่างนี้ว่า causal impact หรือ learning gain ที่พิสูจน์แล้ว

### กติกาที่ต้องยืนยันก่อนระบบจริง

รายการต่อไปนี้เป็นข้อเสนอสำหรับ UX prototype ไม่ใช่ business rule ที่ผู้ใช้ยืนยันแล้ว:

1. หากมีหลาย attempt ต่อ stage ให้เลือกผลใด: ครั้งแรก, ครั้งล่าสุด, คะแนนสูงสุด หรือ attempt ที่ผู้สอนกำหนด
2. แนะนำให้ต้นแบบใช้ attempt ที่ส่งสำเร็จครั้งแรกต่อ stage ในการเทียบ Pre/Post เพื่อให้เห็นผลพื้นฐานโดยไม่เลือกเฉพาะคะแนนดีที่สุด; attempt อื่นยังแสดงในประวัติ แต่ไม่เปลี่ยน paired result จนกว่าจะเลือกกติกาจริง
3. ต้องการให้ Pre-test เป็นงานบังคับก่อนเริ่มเรียนหรือไม่ และจะจัดการผู้เรียนที่เข้าคอร์สช้าหรือข้ามแบบทดสอบอย่างไร
4. ผู้สอนแก้ผลตรวจย้อนหลังได้หรือไม่; ถ้าได้ ต้องเก็บประวัติผู้แก้และเวลาที่แก้ใน Production
5. กำหนด threshold “ต้องติดตาม” จากอะไร; ห้าม hard-code score/risk cutoff โดยไม่มีการยืนยัน

หากยังไม่มีคำตอบ ให้แสดงการเปรียบเทียบจาก fixture พร้อม label “ตัวอย่าง” และคำอธิบายสูตร ไม่ล็อกกติกาเป็น Production

## 9. Metric dictionary สำหรับ MVP

| Metric | นิยามที่ใช้ในหน้าจอ | ข้อจำกัด/การแสดงผล |
| --- | --- | --- |

| เรียนจบ | ผ่าน/ทำครบตาม completion rule ของรายการใน curriculum | ระบุว่าเป็นสถานะที่บันทึก ไม่ใช่เวลาหรือความเข้าใจ |

## 10. สิทธิ์ ความเป็นส่วนตัว และการเข้าถึง

- ผู้สอนเห็นเฉพาะ course scope ที่ตนเป็นเจ้าของ แม้เปิด URL ตรงหรือปรับ query string
- แอดมินเห็นทุก course ตาม prototype role; aggregate ก่อน drill-down และบอกบริบททุกครั้ง
- ใน Production ต้องตรวจ permission ฝั่ง server/domain action ด้วย การซ่อนเมนูหรือ client route guard ไม่ใช่ security
- หลีกเลี่ยง PII ที่ไม่จำเป็น; ไม่ทำ export ใน MVP และไม่แสดงคำตอบรายบุคคลใน aggregate chart
- สถานะใช้ทั้งข้อความและสี; field/button มี label, keyboard focus, touch target และตารางใช้งานบนมือถือได้
- ใช้ Ant Design/table patterns ที่ติดตั้งและ token สี/ฟอนต์ของ prototype ปัจจุบัน; ไม่สร้าง design system หรือสี accent ชุดใหม่

## 12. เกณฑ์รับงานรอบ UI ต้นแบบ

- ผู้สอนบัญชี A เปิด Analytics ได้เฉพาะคอร์ส A; ผู้สอนไม่มีคอร์สเห็น empty state ที่มีทางออก
- แอดมินเลือกผู้สอน/คอร์สแล้ว drill-down ได้ และทุกหน้าระบุ context ชัด
- คลิก metric งานรอตรวจจาก Analytics แล้วได้ queue ที่ filter ตรง; ตรวจและบันทึกแล้วกลับบริบทเดิมได้
- Learner detail แสดงเฉพาะงาน/คะแนนของ learner คนนั้นในคอร์สที่เลือก; ไม่มีคำตอบของคนอื่น
- Pre/Post จับคู่ด้วย learner ID + course/enrollment scope + comparison set, แสดง matched n และแยก unmatched/pending
- คำนวณ paired percentage-point difference จากคะแนน normalized ที่ valid; ไม่มีการเฉลี่ย pending หรือการรวม attempt ซ้ำเป็นผู้เรียนเพิ่ม
- ค่าไม่มีข้อมูลแสดง “—” และเหตุผล ไม่แสดงศูนย์ปลอม; metric ทุกตัวมี definition หรือ tooltip/help text
- Direct route, no access, not found, loading, empty, error, pending grading, zero score และ mobile table behavior มี state ที่เหมาะสม
- การจัดวางยึดธีมที่มีอยู่: พื้นขาว/ฟ้าอ่อนเย็น, primary cobalt เดิม, neutral text/shadow, Anuphan และ Ant Design; ไม่ทำหน้าเป็นกอง metric cards
- ไม่มี endpoint, payment provider, event tracking, AI/MCP write permission หรือ claim ว่าเป็น Production เพิ่มเข้ามาในงาน UI นี้
