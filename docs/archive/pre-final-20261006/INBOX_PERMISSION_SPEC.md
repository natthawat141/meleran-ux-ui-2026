# กติกาสิทธิ์และเส้นทางข้อความของอินบ็อกซ์

วันที่ยืนยัน: 1 ตุลาคม 2026

สถานะ: ผู้ใช้ยืนยันกติกาด้านผลิตภัณฑ์ต่อไปนี้แล้ว เอกสารนี้เป็นแหล่งกลางสำหรับงานอินบ็อกซ์ ใช้ร่วมกับ [UI_SPEC.md](../../UI_SPEC.md) และ [CODE_SPEC.md](../../CODE_SPEC.md)

**การยืนยันเอกสารไม่เท่ากับ implementation เสร็จแล้ว** แอปปัจจุบันเป็น UX prototype ที่เก็บข้อมูลในเบราว์เซอร์ ยังไม่มี backend ที่บังคับสิทธิ์จริง เอกสารนี้ไม่ตัดสินสแตก สถาปัตยกรรมบริการ หรืออนุญาต deployment

## 1. วัตถุประสงค์และขอบเขต

- ให้ผู้เรียนถามเรื่องบทเรียนกับผู้สอนของคอร์สที่มีสิทธิ์เรียน และขอความช่วยเหลือเรื่องบัญชี/การใช้งานจากทีมดูแล
- การอนุญาตต้องพิจารณาทั้งบัญชี บทบาท ความสัมพันธ์กับคอร์ส ผู้ร่วมบทสนทนา และการมอบหมายงาน ไม่ตรวจเพียงชื่อ role
- รุ่นแรกไม่เปิดแชตระหว่างผู้เรียน ไม่เปิดส่งหาผู้สอนทุกคน และไม่เปิดให้ผู้สอนเริ่มข้อความส่วนตัวถึงผู้เรียนคนใดก็ได้

## 2. ตารางสิทธิ์ที่ยืนยันแล้ว

| เส้นทาง | เริ่มเรื่องใหม่ | ส่งต่อ/ตอบกลับ | อ่านประวัติ |
| --- | --- | --- | --- |
| ผู้เรียน → ผู้สอน | เฉพาะผู้สอนของคอร์สที่ผู้เรียนมีสิทธิ์เรียนอยู่ | ต้องเป็นบทสนทนาของตนในคอร์สที่ยังมีสิทธิ์เรียน | อ่านประวัติของตนได้แม้สิทธิ์เรียนหมด หากบัญชียังใช้งานได้ |
| ผู้สอน → ผู้เรียน | ไม่เปิดการเริ่มข้อความถึงผู้เรียนเองในรุ่นแรก | ตอบเฉพาะบทสนทนาที่ส่งถึงตนในคอร์สที่ตนรับผิดชอบ | เฉพาะบทสนทนาที่ตนมีสิทธิ์ ไม่มีสิทธิ์จาก role ผู้สอนอย่างเดียว |
| ผู้เรียน → ทีมดูแล | เปิดเรื่องบัญชี/การใช้งานผ่านช่องติดต่อทีมดูแล | ต่อเรื่องของตนได้ รวมถึงเมื่อสิทธิ์เรียนหมด | เฉพาะเรื่องของตน |
| แอดมินผู้รับมอบหมาย → ผู้เรียน | ไม่เปิดการเริ่มข้อความส่วนตัวถึงผู้เรียนเองในรุ่นแรก | ตอบเฉพาะเรื่องสนับสนุนที่ได้รับมอบหมายและยังมีสิทธิ์ดูแล | เฉพาะเรื่องที่ได้รับมอบหมายตามสิทธิ์ |
| ผู้เรียน → ผู้เรียนอื่น | ไม่อนุญาต | ไม่อนุญาต | ไม่มีสิทธิ์อ่านบทสนทนาของผู้อื่น |
| ผู้เรียน → ผู้สอนคอร์สอื่น | ไม่อนุญาต | ไม่อนุญาต | ไม่มีสิทธิ์จากการรู้รหัสผู้สอนหรือบทสนทนา |

แอดมินทั่วไป **ไม่มีสิทธิ์อ่านแชตผู้เรียน–ผู้สอนทั้งหมดโดยอัตโนมัติ** สิทธิ์จัดการคอร์สหรือผู้ใช้ไม่ทำให้ได้สิทธิ์อ่านข้อความส่วนตัวเพิ่ม หากต้องมีการตรวจสอบเรื่องร้องเรียนในอนาคต ต้องกำหนดกระบวนการและสิทธิ์เพิ่มเติมก่อน

## 3. การเลือกผู้รับและบริบทคำถาม

### ถามผู้สอน

1. ผู้เรียนกดถามจากคอร์ส บท วิดีโอ บทอ่าน หรือแบบฝึกหัด หรือเลือกคอร์สที่ติดต่อได้จากอินบ็อกซ์
2. ระบบตรวจสิทธิ์เรียนและหาผู้สอนจากข้อมูลคอร์ส ผู้เรียนไม่ต้องกรอกรหัสผู้รับเอง
3. ระบบตรวจว่าบทและรายการเนื้อหาเป็นของคอร์สนั้นจริง แล้วแนบชื่อคอร์ส/บท/เนื้อหากับข้อความที่ส่ง
4. บริบทอยู่ต่อข้อความ คำถามจากคนละบทใช้บทสนทนาเดียวของคอร์สได้โดยยังแยกต้นทางของแต่ละคำถาม
5. เก็บชื่อ ณ เวลาส่งไว้เป็นบริบทประวัติ แต่การสร้างลิงก์กลับไปเนื้อหาต้องตรวจว่าเนื้อหายังอยู่และบัญชีมีสิทธิ์เปิด ไม่ให้ snapshot เป็นช่องทางข้ามสิทธิ์เรียน

การถามจากภาพรวมคอร์สไม่ต้องสร้างบทสมมติ การถามจากบทที่ไม่ได้เลือกรายการเนื้อหาแนบเฉพาะคอร์สและบทได้

### ติดต่อทีมดูแล

- ผู้เรียนเลือกช่อง **“ติดต่อทีมดูแล”** สำหรับเรื่องบัญชีและการใช้งาน แทนการเลือกส่งถึงแอดมินทุกคนเป็นรายบุคคล
- ระบบมอบหมายผู้รับผิดชอบ และให้ผู้รับมอบหมายตอบเรื่องนั้นได้
- กล่องทีมดูแลไม่ได้หมายความว่าแอดมินทุกคนอ่านรายละเอียดได้ ผู้ที่ไม่ได้รับมอบหมายต้องไม่เห็นข้อความหรือข้อมูลที่เผยเนื้อหาของเรื่องโดยอัตโนมัติ
- วิธีมอบหมาย ผู้มีสิทธิ์คัดแยกเรื่อง และการเปลี่ยนผู้รับผิดชอบยังต้องออกแบบเพิ่มเติม ไม่ถือว่า role แอดมินให้สิทธิ์เหล่านี้ครบแล้ว

## 4. เมื่อสิทธิ์เรียนหมดหรือข้อมูลเปลี่ยน

- ผู้เรียนอ่านประวัติสนทนาเดิมของตนได้ แต่เริ่มเรื่องใหม่หรือส่งต่อถึงผู้สอนของคอร์สที่หมดสิทธิ์ไม่ได้
- UI แสดงว่าหมดสิทธิ์ส่งคำถามในคอร์ส พร้อมช่องทางติดต่อทีมดูแล ข้อความที่พิมพ์ไว้ต้องไม่ถูกส่งหรือทิ้งเงียบ ๆ
- การหมดสิทธิ์เรียนไม่ตัดช่องทางติดต่อทีมดูแลเรื่องบัญชี/การใช้งาน
- บัญชีที่ถูกระงับหรือไม่มี session ที่ใช้ได้ต้องไม่ส่งข้อความ การอ่านประวัติหลังสิทธิ์เรียนหมดไม่ได้อนุญาตให้ข้ามการยืนยันตัวตนหรือสถานะบัญชี
- เมื่อเปลี่ยนผู้สอน ผู้รับผิดชอบ หรือองค์กร ต้องตรวจสิทธิ์ใหม่ ผู้สอนคนใหม่ไม่ได้สิทธิ์อ่านแชตส่วนตัวเดิมอัตโนมัติจากการเป็นเจ้าของคอร์ส
- ยังไม่ตัดสินวิธีโอนแชตเมื่อเปลี่ยนผู้สอน หรือสิทธิ์เก็บประวัติของผู้สอนคนเดิม ห้ามเพิ่มสิทธิ์โอน/อ่านย้อนหลังเองระหว่าง implementation

## 5. ข้อกำหนดสำหรับระบบจริง

- ฝั่ง server ตรวจสิทธิ์ทุกครั้งสำหรับสร้างเรื่อง แสดงรายการ เปิด/อ่านข้อความ ส่งข้อความ และทำเครื่องหมายอ่าน ไม่ใช้การซ่อนปุ่มหรือ route guard เป็นหลักฐานว่าสิทธิ์ปลอดภัยแล้ว
- ระบุผู้ส่งจาก session ที่ยืนยันแล้ว ไม่เชื่อ `senderId`, role หรือรายชื่อผู้ร่วมสนทนาที่ client ส่งมา
- ตรวจผู้รับ สิทธิ์เรียน เจ้าของคอร์ส และบท/เนื้อหาจากข้อมูลที่ server ควบคุม แม้ client เปลี่ยน query หรือเรียก API เองก็ต้องไม่ข้ามกติกาได้
- การตอบในบทสนทนาต้องตรวจสิทธิ์กับบทสนทนานั้นใหม่ ไม่ใช้การมีรหัสบทสนทนาเป็นหลักฐานอนุญาต
- ถ้าระบบรองรับหลายองค์กร ต้องตรวจขอบเขตองค์กรทุกครั้ง และไม่เปิดค้นหารายชื่อหรือส่งข้อความข้ามองค์กรโดยอัตโนมัติ รูปแบบองค์กรและ schema ยังไม่ถูกกำหนดจากเอกสารนี้
- รายการสนทนา ผลค้นหา จำนวนยังไม่อ่าน แจ้งเตือน และข้อความตัวอย่างในแจ้งเตือนใช้ขอบเขตสิทธิ์เดียวกัน ไม่เปิดเผยข้อมูลจากบทสนทนาที่อ่านไม่ได้
- การเข้าถึงที่ไม่ได้รับอนุญาตต้องไม่ส่งเนื้อหาหรือข้อมูลคู่สนทนากลับมา ใช้ข้อความผิดพลาดที่ไม่เผยรายละเอียดของเรื่องส่วนตัว

## 6. ป้องกันการส่งรัวและข้อความซ้ำ

Permission กำหนดว่าใครติดต่อใครได้ ส่วนการป้องกันการส่งรัวต้องมีมาตรการแยกกัน:

- จำกัดความถี่การส่งที่ server ไม่ใช้การหน่วงปุ่มบนหน้าจอเพียงอย่างเดียว
- ป้องกันคำขอเดิมที่กดส่งซ้ำหรือ retry ทำให้เกิดข้อความและแจ้งเตือนซ้ำ
- เมื่อส่งไม่สำเร็จ แสดงเหตุผลที่เหมาะสมและรักษาฉบับร่าง ไม่แสดงว่าส่งสำเร็จล่วงหน้า
- มีช่องทางรายงานการใช้งานที่เป็นปัญหา โดยกระบวนการตรวจเรื่องและผู้มีสิทธิ์ตรวจต้องกำหนดเพิ่มเติม
- ตัวเลขเพดานการส่ง ช่วงเวลา ขนาดข้อความ/ไฟล์แนบ และขั้นตอนจัดการรายงานยังไม่ยืนยัน ห้ามถือค่าที่อยู่ในต้นแบบเป็นกติกา Production ที่อนุมัติแล้ว

## 7. สถานะต้นแบบและงานที่ยังต้องทำ

ตรวจเทียบ source ณ วันที่ 1 ตุลาคม 2026:

| ส่วน | ต้นแบบปัจจุบัน | ส่วนที่ต้องปรับตามกติกานี้ |
| --- | --- | --- |
| ผู้รับผู้สอน | [selectors](../../../src/api/inbox.ts) เลือกผู้สอนตาม enrollment และคอร์ส | ระบบจริงต้องตรวจสิทธิ์เรียนที่ยังมีผล ไม่ใช่เพียงมีแถว enrollment |
| การอ่าน/ส่ง | [store](../../../src/store.tsx) ตรวจ participant และเจ้าของคอร์สใน browser | บังคับที่ server ทุก operation รวมการส่งใน thread เก่า |
| สิทธิ์เรียนหมด | thread เดิมยังส่งต่อได้หากยังเป็น participant | ปิดส่งถึงผู้สอนเมื่อหมดสิทธิ์ แต่เก็บประวัติอ่านและติดต่อทีมดูแล |
| ติดต่อแอดมิน | เลือกบัญชีแอดมินที่ active และสนทนาสองบัญชี | เปลี่ยนเป็นเรื่องทีมดูแลพร้อมการมอบหมาย ไม่เปิดทุกเรื่องให้แอดมินทุกคน |
| บริบทบทเรียน | [ปุ่มถาม](../../../src/components/AskInstructorButton.tsx) ส่งต้นทาง และ store สร้าง snapshot ต่อข้อความ | คงพฤติกรรมนี้ พร้อมตรวจสิทธิ์และข้อมูลที่ server |
| การส่งรัว/รายงาน | จำกัดข้อความ 3,000 ตัวอักษรในต้นแบบ ยังไม่มีระบบจำกัดความถี่หรือรายงาน | ออกแบบและทำมาตรการตามข้อ 6 หลังตกลงรายละเอียด |
| ไฟล์แนบ | [หน้าอินบ็อกซ์](../../../src/pages/inbox/InboxPage.tsx) รองรับภาพ/วิดีโอและ preview โดยบันทึก data URL ใน browser; มีเพดานต้นแบบ 3 ไฟล์, 5 MB ต่อไฟล์, 8 MB รวม | Production ต้องกำหนดชนิด/ขนาดที่อนุมัติและใช้ API/file storage; เพดานต้นแบบนี้ไม่ใช่นโยบายจริง |
| ข้อมูลตัวอย่าง | [fixtures](../../../src/mocks/inbox.ts) เป็นสนทนาตรงแบบเดิมและ merge โดยรักษาข้อมูลผู้ใช้ | ปรับ fixtures ตาม flow ทีมดูแลเมื่อ implementation เปลี่ยน |

งานในรอบที่สร้างเอกสารนี้เป็น **เอกสารเท่านั้น** ไม่ได้เปลี่ยน flow แอดมิน สิทธิ์หมดอายุ หรือเพิ่ม backend เอกสารนี้มีน้ำหนักเหนือคำอธิบายพฤติกรรมต้นแบบเดิมเมื่อเริ่มงานปรับอินบ็อกซ์ครั้งถัดไป

| ผู้สอนคนอื่นหรือแอดมินทั่วไปเปิดแชตผู้เรียน–ผู้สอน | ปฏิเสธ แม้มีสิทธิ์จัดการคอร์สหรือผู้ใช้งาน |
| สิทธิ์เรียนหมดหลังเคยคุยแล้ว | อ่านประวัติของตนได้ ส่งต่อถึงผู้สอนไม่ได้ ติดต่อทีมดูแลได้ |
| คำถามจากหลายบทในคอร์สเดียวกัน | ต้นทางของแต่ละข้อความถูกต้องและคงอยู่หลังเปิดใหม่ |
| ผู้รับมอบหมายตอบเรื่องทีมดูแล | ตอบได้เฉพาะเรื่องที่มีสิทธิ์ ผู้ที่ไม่ได้รับมอบหมายอ่าน/ตอบไม่ได้ |
| คำขอเดิมถูกส่งซ้ำจากการ retry | เกิดข้อความและแจ้งเตือนหนึ่งชุด |
| ส่งเกินเพดานที่ตกลงภายหลัง | ปฏิเสธตามกติกา แจ้งผู้ส่งและรักษาฉบับร่าง |
| หลายองค์กรใช้ระบบเดียวกัน | เปลี่ยนรหัสข้ามองค์กรแล้วอ่าน/ส่งไม่ได้ |
